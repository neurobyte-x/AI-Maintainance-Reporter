High-Level Purpose
What problem does this project solve?
It automates campus maintenance reporting by turning uploaded photos into structured maintenance tickets using AI image analysis, then routes those tickets through role-based workflows (student submits, admin manages). This is implemented in main.py:491, main.py:573, and main.py:637.
What is the main goal of the system?
The main goal is to reduce manual triage by automatically generating issue description, category, and priority from an image, then persisting and tracking ticket lifecycle in PostgreSQL. Core logic is in main.py:258, main.py:305, and DB schema in NEON_SCHEMA.sql.

Key Technical Decisions

FastAPI (API layer), Pydantic (validation/serialization), PyJWT (auth token), psycopg2 (PostgreSQL), LangGraph + LangChain core messages (workflow orchestration/state), Google Generative AI Gemini model (image reasoning), React + Axios (client), Render deployment config. Why are they used in this project?
FastAPI + Pydantic provide concise typed API with automatic validation.

LangGraph provides explicit multi-step AI pipeline instead of one large function main.py:354.
PostgreSQL/Neon supports persistent multi-user ticketing and relational integrity via FK NEON_SCHEMA.sql.
Axios interceptor centralizes auth header handling api.js:26.
Render config aligns backend+frontend build and single-service serving render.yaml.

Explain how it works (step-by-step, with pseudo-code if needed)
Pseudo-flow for ticket creation:

Authenticate token -> extract user_id.
Persist uploaded image to disk.
Run workflow:
analyze_image: call Gemini with maintenance-specific prompt.
classify_issue: map free text to issue_type and priority using keyword sets.
create_ticket: mark completion.
Insert DB row with user_id + inferred fields.
Return structured response.
Pseudo-flow for ticket updates:

Authenticate token.

Load caller role from users.

Load target ticket owner.

If caller is not admin and not owner -> reject.

Build dynamic SQL only for provided fields.

If status field requested by non-admin -> reject.

Execute update and return refreshed ticket.

Edge Cases & Handling

Identify possible failure scenarios (e.g., concurrency, invalid input, scaling issues)
Missing/invalid token -> 401 from main.py:180.
Invalid role/short password -> validation errors from main.py:191.
Duplicate email signup -> 400 in main.py:405.
Missing image file -> 400 in main.py:504.
Gemini/API errors -> converted to text inside analysis result at main.py:258, which can still produce a ticket with fallback classification.
Unauthorized status update/delete -> 403 in main.py:659, main.py:841.
Ticket not found -> 404 in get/update/delete handlers main.py:624, main.py:749, main.py:850.
DB failures -> transaction rollback via context manager main.py:95.
Schema drift risk: runtime init_db definition differs from Neon schema constraints/indexes (main.py:119 vs NEON_SCHEMA.sql).
Client mismatch risk: legacy static client in app.js calls unauthenticated endpoints that now require auth and expects different response shape.

Explain how the system handles them
Auth and validation failures are surfaced with explicit HTTP exceptions and status codes.
Database operations are wrapped in transactional context to avoid partial writes on exceptions.
File cleanup on ticket delete is attempted and non-fatal if file removal fails main.py:861.
Role checks are performed server-side before admin-only actions; ownership checks protect patch endpoint.
